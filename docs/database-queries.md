# Database queries and sqlc

Generated applications pin sqlc `v1.31.1` through a Go `tool`
directive. Queries are handwritten and feature-colocated; there is no ORM,
query builder, schema DSL, or shared repository package.

## Feature layout

```text
internal/features/invoice/
├── domain.go
├── usecase.go
├── sqlc.yaml
├── queries/
│   └── invoices.sql
└── store/
    └── ... generated by sqlc
```

`queries/` and `sqlc.yaml` are application-owned.
`store/` is generated as a complete unit and carries sqlc's native
do-not-edit header. Delete and regenerate the directory instead of editing
it.

## Required config shape

```yaml
version: "2"
sql:
  - name: invoice
    engine: postgresql
    schema: ../../../db/migrations
    queries: queries
    gen:
      go:
        package: store
        out: store
        sql_package: pgx/v5
        emit_interface: true
        emit_empty_slices: true
        query_parameter_limit: 0
        omit_unused_structs: true
```

Paths are relative to the feature-local config. The shared migrations remain
the authoritative schema; a feature must not maintain a second schema
snapshot beside its queries.

`query_parameter_limit: 0` makes even a one-argument operation take a
named parameter struct, so adding another parameter does not change every
call site's signature. `emit_interface` supplies the narrow DBTX-facing
contract used by explicit transaction wiring. `emit_empty_slices`
keeps collection JSON stable as `[]` instead of `null`.

## Commands

From the generated project root:

```sh
make sqlc-compile
make sqlc-generate
```

Both commands discover `internal/features/*/sqlc.yaml` recursively in
stable path order and pass `--no-remote`. They do no work—and return
success with an explicit message—before the first query-owning feature
exists.

sqlc-generated repositories execute queries only. They accept a pgx pool or
transaction implementing the generated DBTX interface; they do not open
pools, begin transactions, authorize users, or translate transport input.
Those boundaries remain visible in application wiring and use cases.

For writes spanning a business operation, the use case calls the generated
application's `database.Transactor.Within` and passes the callback's `pgx.Tx`
to `store.New(tx)`. See [Database transactions](database-transactions.md) for
the lifecycle, cancellation, panic, nested-use, and option contracts.
