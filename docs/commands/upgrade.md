# `nise upgrade`

Moves a generated project to the nise that is running.

```sh
cd my-app
nise upgrade --dry-run   # look first
nise upgrade             # then apply
git diff                 # then review
```

```
Upgraded from nise v0.1.0 (runtime v0.1.0) to v0.2.0 (runtime v0.2.0).

Generated files (2):
  update  internal/app/modules.gen.go
  update  nise.json

Dependencies (3):
  go.mod: github.com/drilonrecica/nise-and-go v0.1.0 → v0.2.0
  go.mod: github.com/go-chi/chi/v5 v5.3.2 → v5.4.0
  frontend/package.json: valibot 1.1.0 → 1.2.0

For you to do (1):
  - v0.1.0 → v0.2.0: sessions gained an explicit idle timeout. Set SESSION_IDLE_TIMEOUT, or accept the 30-minute default.

Next:
  go mod tidy
  pnpm --dir frontend install
  git diff
  nise check
  go build ./...

No application-owned file was regenerated. Review the diff before committing.
```

## The rule everything follows from

Nise owns some files in your project and you own the rest
([ADR 0003](../adr/0003-application-ownership.md)). An upgrade is where that
rule is under the most pressure: the framework has changed, your code may need
to change with it, and the tempting shortcut is to regenerate everything and
let you sort it out from the diff.

That is not an upgrade. It is a restore from a backup nobody took.

So `nise upgrade` does four separate things, ordered by how much each is
allowed to touch.

### 1. Nise-owned files are regenerated

Files carrying `Code generated by nise; DO NOT EDIT.` are the framework's to
rewrite, and an upgrade is exactly when they have to move. If you edited one,
your edit is replaced — that is what the header means.

A file a migration declares this version stopped writing is deleted. An
orphaned `.gen.go` from a subsystem that no longer exists does not stop
mattering when it stops being written: it still compiles, and still refers to
things that may not.

Removals are **declared** by the migration rather than discovered, and they
have to be: an upgrade can only plan your project with the templates it *has*,
so the file set an older nise wrote is not something a newer one can compute.

### 2. Pinned dependencies are bumped

Every requirement nise pins is moved forward — in `go.mod` and in the generated
`frontend/package.json`. Only the version token on that requirement's own line
changes.

Both files are yours, so three things follow:

- **A requirement you removed stays removed.** An upgrade that re-added a
  dependency you deliberately dropped has overruled you.
- **A requirement you pinned *ahead* of nise stays ahead**, and is named in the
  output. Moving it back would be a downgrade wearing an upgrade's name, and it
  would silently revert whatever you took the newer version for.
- **Nothing is reformatted.** `go mod edit` would reorder the require block and
  drop the comments; re-encoding `package.json` would reorder its keys. Either
  turns a three-line diff you can read into a whole-file one you will scroll
  past.

`go mod tidy` and `pnpm install` are **named, not run**. Both resolve a
dependency graph over the network, and an upgrade must not be the command that
discovers a dependency is unreachable — least of all halfway through writing
files. `nise upgrade` performs no network access at all
([no-telemetry.md](../no-telemetry.md)).

### 3. Declared codemods rewrite application source

A codemod is an **exact textual replacement** a migration declares — an import
path, a qualified identifier. There is no AST rewriting, no import reordering,
no formatting pass.

Exact and textual is the whole safety argument. An AST rewrite is more powerful
and can be wrong in ways you will not notice in a diff; a literal replacement
of a string that does not occur is a no-op, and one that does occur shows up in
`git diff` as precisely the substitution that was announced. Every application
is counted and reported with its file, so a codemod that fires somewhere
unexpected is in the output rather than only in your working tree.

Codemods touch only files nise generated *as yours* — the plan says which. A
directory walk would also reach vendored code, `node_modules`, and whatever
else is in your tree.

`--no-codemods` refuses them. You then get the instruction as a note instead of
the edit, so you still learn the change exists.

### 4. Everything else is a note

A change that needs judgement is printed for you to make, not guessed at.

This is the category that keeps the other three honest. The moment a migration
is tempted to rewrite application logic, it writes a paragraph instead.

## The working tree must be clean

`git diff` is the review, and a diff that also contains half a feature you were
in the middle of is not one anybody reads. So an upgrade refuses to start on a
dirty working tree:

```
the working tree has uncommitted changes, and an upgrade's diff is how you review it
Commit or stash your work first, then run nise upgrade again. Use --dry-run to see what it would do, or --force to mix the two.
```

Committing first costs a minute and makes the upgrade a single revertible
commit.

`--dry-run` is never refused — looking is always safe — and a project that is
not a git repository is not refused either. `nise new` never runs git, and
requiring a repository would be inventing a prerequisite.

## An older nise refuses to upgrade

```
this nise is older than the one that last touched the project
```

An older nise cannot know what a newer one wrote, and regenerating with it
would quietly revert files. Install the newer nise and run it there.

A nise built from a source checkout is not refused: it reports a version no
parser can order, and refusing there would make the framework's own development
loop unusable. The ownership rules protect your project either way.

## Flags

| Flag | Effect |
|---|---|
| `--dry-run` | Report what would change and write nothing. |
| `--no-codemods` | Never rewrite application source; report every such change as a note. |
| `--force` | Upgrade despite uncommitted changes. |

## Exit codes

| Code | Meaning |
|---|---|
| 0 | The upgrade completed, or the project was already current. |
| 1 | Something went wrong while writing. |
| 3 | A precondition failed: not a project, a dirty tree, or a downgrade. |

## What it writes, and in what order

1. Nise-owned files.
2. Codemods, so a rewritten import lands in a tree whose generated half is
   already the new one.
3. Dependency manifests, which are what `go mod tidy` reads next.
4. The recipe, **last**. It is the record that the upgrade happened, and
   writing it first would leave a project claiming to be upgraded after a
   failure halfway through.

Every write goes through a root opened on the project directory, so a path can
only ever resolve inside it. The paths come from nise's own generator, so that
is not defence against an attacker — it is defence against a symlink somebody
put in their project, and against a command that writes into your working tree
having no business being able to reach outside it.

## Skipping versions

Migrations are declared per consecutive version pair and chained
automatically. A gap in the chain is **reported, not skipped**:

```
No migration is declared from v0.2.0, so nothing was applied for the versions
after it. Read the release notes between v0.2.0 and v0.4.0 before relying on
this upgrade.
```

An upgrade that silently jumped over a missing link would leave a project
half-migrated with nothing in the output to say so.

## After an upgrade

```sh
go mod tidy
pnpm --dir frontend install   # if the frontend manifest changed
git diff
nise check
go build ./...
```

`git diff` comes before the checks on purpose. The point of an upgrade that
never overwrites application code is that you can read what it did.
