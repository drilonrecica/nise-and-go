# Your first Nise application

Thirty minutes, from nothing installed to an application running against a real
PostgreSQL, with a feature you added yourself.

Everything on this page has been run in the order it is written. Where output
is shown, it is what the command actually printed.

**Before you start**, know what this project is: pre-alpha, personal, and
maintained by one person with no support or review SLA
([project status](project-status.md), [governance](../GOVERNANCE.md)). Build
something with it because the shape of it appeals to you, not because you are
relying on it.

---

## 1. Install nise

Three ways, and they install the same release.
[Verify what you downloaded](cli-and-distribution.md#verifying-a-download)
before you run it — the second check on that page is the one that matters.

```sh
# Homebrew
brew install drilonrecica/tap/nise

# Go, at an exact version
go install github.com/drilonrecica/nise-and-go/cmd/nise@v0.1.0

# Or download the archive for your platform from the releases page.
```

```sh
nise version
```

Nise never updates itself and never checks for updates on its own. When you
want to know, ask:

```sh
nise version check
```

That is the only command in nise that opens a network connection
([why, and what it sends](commands/version.md)).

```sh
nise doctor
```

```
[SKIPPED] sqlc

    …

```

Four things have to be on your machine: Go, Node, pnpm, and Docker or Podman.
Everything else a project needs is pinned by the project itself — which is why
`sqlc`, `goose`, and `oapi-codegen` skip here and are checked once you are
inside one.

Anything that fails prints the command that fixes it.

## 3. Create a project

```sh
nise new bookshop
```

It asks two or three questions, or takes `--yes` to accept the defaults.
Generation writes files and does nothing else: no network, no `go`, no `pnpm`,
no `git`. That is why it is fast and why running it twice produces the same
bytes.

```sh
cd bookshop
```

> **While Nise is pre-release**, the framework module is not on the Go module
> proxy yet, so a fresh project cannot resolve it:
>
> ```sh
> go mod edit -replace github.com/drilonrecica/nise-and-go=/path/to/your/nise-and-go
> ```
>
> `nise new` prints this too. It goes away with the first published release.

```sh
go mod tidy
pnpm --dir frontend install
```

Both are needed before `nise test` can run the component suite; without the
second it reports that suite as skipped and tells you this exact command.

Have a look at what you got — the layout is
[documented in full](generated-application-layout.md), and the short version
is that everything under `internal/features/` is yours, and the handful of
files carrying `Code generated by nise; DO NOT EDIT.` are not.

## 4. Run it

```sh
nise dev
```

This starts PostgreSQL in a container, applies the migrations, runs the Go
server and the Vite dev server, and puts both behind one origin so there is no
CORS to configure. Open the URL it prints.

You will land on a sign-in page, because there is no public registration:
enrollment is by invitation ([why](enrollment.md)). Make yourself the first
account:

```sh
./bookshop admin bootstrap --email you@example.com
```

It prints an invitation token. Use it on the sign-in page's invitation link,
choose a password, and you are inside the application shell.

## 5. Check it

```sh
nise check
```

```
7 ok, 0 fail, 2 skipped
```

This is not a linter. It asks whether the invariants Nise guarantees still
hold in *your* project: that generated files still declare who owns them, that
regenerating reproduces them byte for byte, that no secret is committed. Run it
in CI. [What each check protects](checks.md).

```sh
nise test
```

## 6. Add something of your own

A feature is a vertical slice: a domain, a use case, and its tests.

```sh
nise generate feature catalogue
```

It writes four files and then prints the changes to make **by hand**, with the
exact code and where it goes. That is deliberate: nise writes new files and
edits none of yours ([ADR 0026](adr/0026-feature-generation-writes-only-new-files.md)),
so every change to a file you own stays in your own diff.

For a full CRUD resource with an API path, a migration, and Svelte pages:

```sh
nise generate resource book
```

Read what it wrote before you run anything else, and then do what it says.
**The project will not compile until you have**: the scaffold declares a
permission, a use case, an API path, and a migration, and it deliberately
wires none of them into files you own. Its output ends with the four commands
to run afterwards, in order:

```sh
make sqlc-generate       # write the query code from the SQL it added
make api-generate        # regenerate the strict server bindings
make api-types-generate  # and the frontend's models, from the same contract
make migration-test      # apply the new migration to a disposable database
```

It invents no fields — a `Book` has an identifier, a name, and timestamps, and
everything else is a decision only you can make.

## 7. Change the database

Migrations are handwritten SQL, applied by an explicit command, never on
startup ([why](database-migrations.md)).

```sh
# Write db/migrations/0001X_something.sql, then:
nise db status
nise db migrate
```

Queries live beside the feature that uses them and are compiled by sqlc, so a
query that does not match the schema fails the build rather than the request
([how](database-queries.md)).

## 8. Deploy it

```sh
pnpm --dir frontend install     # produces the lockfile the image needs
docker build -f deploy/Dockerfile -t bookshop .
```

The image is about 18 MB: a static binary and a non-root user, with no shell
and no package manager. Try `docker run --rm --entrypoint /bin/sh bookshop` and
it will tell you there is no shell to run.

For a whole stack — database, an explicit migration step, then the application:

```sh
cd deploy
POSTGRES_PASSWORD=… CURSOR_SIGNING_KEY="k1:$(openssl rand -base64 32)" \
  docker compose up -d --build
```

Then `/healthz`, `/readyz`, and `/startupz` on port 8080.

Production **fails closed**, and the first time you deploy you will meet it: it
refuses to start without a cursor signing key, refuses the log mail transport
because an application that silently sends no invitations is worse than one
that will not start, and — if you selected the organizations module — refuses a
database role that can bypass row-level security. Each refusal names the
setting. [Deployment](deployment.md), and
[Coolify](../examples/reference/README.md) for a platform that does the rest.

## 9. Back it up, and prove it

```sh
export BACKUP_ENCRYPTION_KEY="$(openssl rand -base64 32)"
./bookshop db backup -out /backups/bookshop-$(date +%F).backup
./bookshop db verify -from /backups/bookshop-$(date +%F).backup
```

`db verify` **restores** the backup into a scratch database and drops it again,
rather than checking a checksum. A backup nobody has restored is a hypothesis.

Read [Backups](backups.md) before you rely on any of this — particularly
[where the key lives](backups.md#key-custody-and-rotation), because a lost key
is lost data and there is no recovery.

## 10. Keep up

```sh
nise version check     # is there a newer nise?
nise upgrade           # move this project to it
```

`nise upgrade` regenerates the files nise owns, bumps the dependencies it pins,
applies the exact textual codemods a migration declares, and **prints
everything else for you to do**. It refuses to start on a dirty working tree,
because `git diff` is how you review what it did.
[What it will and will not touch](commands/upgrade.md).
