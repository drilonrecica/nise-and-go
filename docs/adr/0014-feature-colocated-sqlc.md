# 0014: Keep sqlc configuration with each feature

- Status: Accepted
- Date: 2026-08-29
- Supersedes: ADR 0009's single root `sqlc.yaml` ownership decision

## Context

Nise requires handwritten SQL to live with the feature that owns it, while
every feature's sqlc output must be reproducible and replaceable as a complete
`store/` directory. A single root `sqlc.yaml` would be a central
registry: every generated or application-added feature would have to edit the
same file, and later generation could not safely add an entry without either
overwriting application changes or using fragile marker insertion.

The alternative of one shared database query package was also rejected. It
would separate a feature's SQL from its use cases, encourage imports across
feature boundaries, and make ownership less visible.

## Decision

Every feature that owns queries has this local contract:

```text
internal/features/<feature>/
├── sqlc.yaml       # application-owned
├── queries/        # application-owned handwritten SQL
└── store/          # sqlc-owned generated Go; never hand-edited
```

The feature's `sqlc.yaml` resolves paths from its own directory, points
`schema` at `../../../db/migrations`, reads `queries/`, and
emits to `store/` with `sql_package: pgx/v5`. It enables the
generated `Querier` interface, empty slices for `:many`,
parameter structs for every query, and omission of table structs unused by
that feature.

The generated project pins sqlc as a Go tool. `make sqlc-generate` and
`make sqlc-compile` discover feature configs, sort their paths under the
POSIX locale, and invoke the local tool with remote execution disabled. An
empty feature tree succeeds with an explicit message rather than inventing a
dummy query package.

Source migrations and query files are application-owned. Files under
`store/` retain sqlc's native
`Code generated by sqlc. DO NOT EDIT.` marker; in this path, that marker
is the machine-readable ownership declaration.

## Consequences

- A feature can be added or removed without editing a central registry.
- Query code cannot accidentally land in another feature's package.
- Application owners can customize each sqlc config after generation.
- Global options are intentionally repeated. This small duplication makes
  each feature independently understandable and avoids hidden defaults.
- A deliberate option change across all features is a mechanical,
  reviewable edit rather than a global switch with invisible effects.
- The generated Makefile uses POSIX shell discovery. The CLI's later
  generation/check commands must implement the same sorted discovery in Go
  for environments that do not use Make.
